## Inside the CPU

A mutex isn't magic.

Internally, it uses **atomic CPU instructions** (hardware-supported operations).

Conceptually, the mutex has a state:

```
locked = 0   // unlocked
locked = 1   // locked
```

Each goroutine tries to do something conceptually like:

```
if locked == 0 {
    locked = 1
    // I got the lock!
}
```

But **this is NOT done as two separate operations**.

Instead, the CPU provides an **atomic** instruction that means:

> "Check if it's 0 and change it to 1 as one indivisible operation."

---

## Suppose all 8 try simultaneously

```

G2 ─┤
G3 ─┤
G4 ─┤──> Atomic Lock
G5 ─┤
G6 ─┤
G7 ─┤
G8 ─┘
```

The CPU and its memory subsystem serialize these atomic operations.

Only **one** atomic operation succeeds.

For example:

```
G5 succeeds

locked: 0 → 1
```

The others see:

```
locked == 1
```

So they fail and block.

* The Go scheduler

These happen at a level far below your Go program.

Even if, from your perspective,

```

the hardware never treats all eight lock acquisitions as happening simultaneously.

Atomic operations establish a **single global order** for that memory location.

So it becomes something like:

...
```

### This is why atomic instructions exist

Without atomic instructions, a mutex itself would suffer from race conditions!

So the hierarchy is:

```

       ↓
sync.Mutex

Go runtime

```

That's why `sync.Mutex` is reliable even when many goroutines on many CPU cores try to lock it "at the same time." The hardware ensures there is always exactly one successful acquisition.

They don't disappear.

3. When the mutex is unlocked, Go wakes one waiting goroutine, which then tries to acquire the lock again.

### One small clarification

When people say "the CPU selects one," that's a useful mental model, but the reality is slightly more nuanced. The CPU hardware and its cache-coherence protocol make the **atomic CAS instruction** behave as if only one thread/goroutine successfully changed the value. The Go scheduler decides which goroutines get CPU time, but **the atomic instruction itself guarantees that only one CAS succeeds** when they race on the same memory location.

So your understanding is correct:

* ✅ 8 goroutines call `Lock()` at the same time.
* ✅ They all attempt a CAS on the mutex state.
* ✅ Only one CAS succeeds.
* ✅ Which goroutine wins is **not deterministic**.
* ✅ The others fail the CAS and wait (spin briefly or sleep, depending on the mutex implementation).

# Case 1: Busy Waiting (Spinning)

This happens **only for a very short time**.

Suppose:

```text
G1 gets the lock
```

The other goroutines may do something like:

```text
Is it free?
No.

Is it free?
No.

Is it free?
No.
```

This is called **spinning**.

During spinning,

* CPU is being used ✅
* Goroutine is running ✅
* It is repeatedly checking the lock ✅

This is good only if the lock will be released very soon (a few nanoseconds or microseconds).

---

# Case 2: Parking (Sleeping)

Suppose G1 is going to hold the lock for a longer time.

Instead of doing this forever:

```text
Is it free?
Is it free?
Is it free?
Is it free?
```

Go Runtime says:

> "Enough. Go to sleep."

So the goroutine is **parked**.

Think of it like this:

```
Runtime:
G2, go sleep.

G2:
Okay 😴
```

Now...

### Is G2 using CPU?

**NO.**

Zero.

It is not executing.

It is not checking anything.

It is literally waiting.

---

# Then who wakes it up?

This is the beautiful part.

When G1 finishes,

```go
mu.Unlock()
```

Go Runtime knows

> "Someone is waiting."

So the runtime wakes one waiting goroutine.

Like:

```
Runtime:

G2!!

Wake up!

The lock might be free.
```

Then G2 becomes runnable again.

It tries to acquire the lock.

---

## So does G2 keep asking?

No.

It is NOT like this:

```

    if(lockFree){
        break
    }
}
```

That would waste CPU.

Instead it's like:

```
G2:
Sleeping...
Sleeping...
Sleeping...
```

No CPU usage.

Then

```
Runtime:

Wake up.
```

Now G2 runs.

# Why spin at all?

Excellent question.

Suppose the critical section is tiny.

```go
mu.Lock()
x++
mu.Unlock()
```

This takes maybe **30 ns**.

If the runtime immediately parks the goroutine, then later waking it up might cost **hundreds or thousands of nanoseconds**.

So it may be cheaper to spin briefly:

```
Is it free?

No.

Is it free?

Yes!

Great!
```

No sleep/wake overhead.

That's why Go's mutex uses a combination of:

```
Try CAS
        ↓
Spin a little
        ↓
Still locked?
        ↓
Park (sleep)
        ↓
Unlock wakes one waiter
```

This hybrid approach gives good performance in both short-lock and long-lock situations.

## One small correction to your wording

You asked:

> "Does the runtime inform him to wake up?"

**YES.** That's the right mental model.

More precisely:

* The goroutine is put into a waiting queue by the Go runtime.
* When `mu.Unlock()` is called, the runtime makes one waiting goroutine **runnable** again.
* The Go scheduler will then schedule that goroutine to run on a CPU. It doesn't necessarily run **immediately**, but it is eligible to run as soon as the scheduler gives it CPU time.
